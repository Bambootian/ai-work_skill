## 0. 怎么读这份记录（先读）

本文每条结论都标了状态，**开工时只有【用户拍定】可以直接当设计输入**：

| 标记 | 含义 | 开工时怎么用 |
|---|---|---|
| **【用户拍定】** | 用户在讨论中明确选定，附原话 | 直接作为设计约束 |
| **【AI 提议·未定】** | 讨论中 AI 提出、用户没有逐条拍板的机制或做法 | 设计时重新论证，可以推翻；不要当成已定 |
| **【待琢磨】** | 用户明说不急着定、需要好好想 | 本轮不要急着定死 |
| **【撤回】** | 讨论中提出、后被数据或用户校正推翻的假设 | 不要重新提出，原因见 §4 |

两条贯穿全文的总原则（均为【用户拍定】）：

1. **大幅精简，但守住契约记忆**：「这块我想做的主要就是精简当前的流程……但又不能完全守不住契约记忆」。
2. **不让过时的约束把模型框住**：「我坚决不希望这些设计过时陈旧且繁重的约束将现有强大模型能力给限制在一个框中，这完全限制了当前时代甚至未来强大模型的思考和智能能力」。

**最容易犯的错**：用一套新的重流程去修旧的重流程。热存储、方向反方、并行，每一项都可能长成新的仪式或新的自造复杂度——
这正是本轮批评的对象。设计时每加一样东西，先问它替换掉了什么。

## 1. 背景与讨论过程

**项目背景（术语表）**：new_review_create 是一个 Python 综述写作 + 引用核验引擎。2026-09-24 重新锚定为「引擎 = 证据与核验服务，
写作与判定交给 Claude Code / Codex agent，流程沉淀为 skill」（下称「09-24 重构」）。n2 = 第二个选题的那份稿，n=3 = 下一个新选题；
「板块 5」= 当前主线；专家 = 两位外部领域专家（回信很慢）；Codex = OpenAI 的 CLI agent，本项目用作跨家族写作 / 审读 / 判定方。
该项目 09-24 以来跑工作流最多（448 个 commit、20 个归档 change），是本轮取证对象。用户是软件工程师，不是该项目的领域（生物医学）专家。

**过程（按时间）**：

1. AI 读 GUIDE、change-loop、FIELD-LOG、20 份回顾和 git 历史，先列 7 条疑似问题，建议形式：终端逐条聊、先对齐用户体感、分层（工具包 / 项目自长约定 / 环境）、只聊到「是不是问题、根子在哪」。
2. 用户逐条回应：确认流程过重（1）、记录只增不减（4）、难读（5）、工具包回路断（6）；第 2 条（gate）看不懂；第 3 条（估算）、第 7 条（10-02→10-06 零提交）是休假 7–8 天所致，予以校正；另补两处亲身别扭（问的题定不了、产物看不懂）。
3. AI 给出初步诊断「人在回路的位置放错了」，派 3 个只读 subagent 取证：62 条裁定按「判不判得了」分类；20 个 change 的 307 条 critic / gate blocking 按类分类。
4. 数据推翻了 AI 自己的「gate 是刀背」假设（§4）。
5. 用户提出「人是船长」与「被锁住的绝世天才」（§2），并指出：方向问题（含本轮工作流问题）都是用户自己想到的，「在此之前，你从来没有质疑过现在是否有问题」。
6. AI 取证：value-review 第一步就是问人「最不满意」、回顾在干活的同一会话内做、无 fresh-context 反方；再派 1 个 subagent 把 212 条真缺陷按根源（问题固有 / 机制带来 / 修复带来）分类。
7. 用户批准回测：在 09-19、09-23 两个仓库快照上，让不加载工作流的全新 agent 做方向审查，与当时工作流内的回顾盲评对比（§3.6）。
8. 讨论方向层反方的触发与人选；用户要求「不要局限于只是加反方这一个问题上」，AI 把全部问题归为四个根子，按 B → A → C → D 逐一讨论，用户逐项拍板。
9. 收尾：写本记录、FIELD-LOG 条目、知识库三条、一页回看网页。

## 3. 问题与证据（按根子）

统计窗口除另注外为 2026-09-24 → 10-14，项目 new_review_create。

### 3.1 根子 A：写进去有机制，读回来、清掉全靠记忆

| 症状 | 数据 |
|---|---|
| watchlist 只增不减 | 106 条，只关 13 条；125KB / 539 行；10-12 那一期新增 21、关 3 |
| decisions 重复、矛盾、悬空 | 91KB；同一件事（Codex 额度停止线）问了 11 次：不设上限 → 60 → 75 → 90 → 用户自行重置 → 90 → 40 → 95（40 当天被改成 95）；API 上限问 3 次；6 条「早定 → 被推翻」链（例：判定时用不用 Claude、怎么用，09-24 / 09-27 / 09-28 三次裁定，10-11 一次全部推翻；广度门两周改 3 次口径） |
| 「读了不行动」 | 近一个月主会话工具调用（09-15→10-15，git 命令已排除，subagent 未计）：watchlist 读约 220 次、decisions 约 230、backlog 约 260、主 spec 约 230；用户基本不读。条目照样悬空——问题不在「没人读」，在「读了只当背景装进上下文，没人比对触发条件、该动手就动手」 |
| 规则写入不对称 | 写：每个 Close 按规则触发（记 gate、写 Errata、更新 backlog、开带触发标签的 watch）。读：只有一条「路由触及该 capability 时复查」，靠 AI 在 539 行里凭记忆对；没有任何条目会自动到期；写新条目前不搜旧条目 |
| 记录多却不成记录 | 复原 20 个 change 的 critic / gate 发现时，约一半 change 记录不全或计数对不上（并进实现 commit、Errata 与 Close 数字不一致等） |
| 测试只加不删 | 被测代码冻结了，测试照样留在每次 Verify 里（见 3.3） |
| 同形：项目自己的引擎问题 | 09-24 重构发现「能力留在探针里没进引擎」；这里是「知识留在记录里没进机制」。项目 Hard Rules 写「可靠性来自机制不来自记忆」，watch 复查本身却靠记忆 |

### 3.2 根子 B：人和 AI 的分工放反了

**裁定分类**（docs/decisions.md 09-24 以来 62 条，subagent 逐条分类，raw/decisions-classified.md）：

| 类 | 条数 | 其中选推荐 |
|---|---|---|
| U 用户判得了（方向、钱、时间、选题、找哪位专家、对外不可逆动作） | 18 | 11 |
| T 用户判不了（技术或领域判断，靠实测或推理本可以定：指标口径、阈值、模型选择、协议细节、引用惯例） | 40 | 33 |
| N 没得选（唯一合理项、确认、记账） | 4 | 2 |

- 用户没选推荐的子项共 8 个：4 个关于额度，2 个是用户自己提的，技术方面只有 2 个——**用户的有效输入集中在钱、时间、方向上**。
- 40 条 T 里有 9 条把额度 / 买不买工具（U）和技术问题捆在同一问里，用户真正该拍的部分被埋住。
- 只有 2 条记有用户原话；6 处是 AI 订正自己出的题（含「选项文字是我写的，有歧义」）——部分 [decide] 的难度是 AI 出题时造出来的。
- 难撤回的只有 6 条。
- 用户的知识库页 Human-in-the-Loop 早有原则：「不要把没有正确答案的裁决升级给人——人总会给答案，但没有东西能证成或证伪它」「护栏写由人判断，却没人问哪个人、他判得了吗」。工作流在元层面违反了它。

**文档名义写给人、实际写给 agent**：Now 段、回顾、commit message 里满是内部代号（⑩⑪⑫、4c-2、D11、L0）；commit subject 常是一整段话；
09-23 一天里每次收工写 Now 段都超 8KB、hook 响四五次（FIELD-LOG 09-23 已记）。change 契约的 Outcome 要求「用户可见词汇」，但「用户」
有歧义（North Star 用户还是操作者本人），常被写成实现层的话。回测里外部反方的报告比工作流内回顾好读得多——文档写给谁，决定它好不好读。

**方向问题全靠人发现**：
- value-review 的第一步就是问人「这段时间你用下来最不满意的一件事是什么？」（`skills/value-review/SKILL.md:30`）——发现问题从设计上交给了人。10-12 用户答「没有」，那次回顾就判「在线」。
- 回顾在干活的同一会话内做，没有 fresh-context 反方；gate 有。同一个 AI 在 gate 位置（看不到推理、立场找问题）70% 发现是真缺陷；在回顾位置两次给出框内结论（09-19 判「继续」；09-23 判「原定终态达成」，次日被证明前提不成立）。
- 09-24 重构由用户一句「一直在打磨生成器……N=3，4，5 的时候是不是每次都要这么修」触发；支撑重构的事实（七轮审稿里正文生成一次没重跑、连续 5 个 change 记「仍未验」、收敛环 0 轮）早在文件里。
- 本轮对话也是例子：AI 的第一份问题清单是用户开口后才列的；「gate 是刀背」是 AI 提的，并且错了。

### 3.3 根子 C：约束还在防旧模型的失败

| 症状 | 数据 |

| 单个 change 文档很重 | 一个只给 verify 加一个读数的 R1（breadth-gate-per-paragraph）spec-lite 13.6KB；writing-review-form 的 tasks.md 58KB |

| 规则叠加成框 | 「主线段只经回顾批准增删」「语义模糊停下问」「不加未被要求的范围」「改预期行为先改 spec」「Outcome 三分类」，单条都合理，叠在一起 + 「用户裁定」标签的粘性 = AI 最理性的做法是在框里推进、不质疑框 |

用户认可「约束防的是旧失败模式」：那些失败（跑偏、加戏、范围蔓延）是更早模型时代的问题。

### 3.4 根子 D：主线单链推进，等待期没事做

- 主线是单链有序列表，change 一个接一个；等待专家回信 / 额度时只能停（第 1 步等专家回件已 18 天）。
- 用户的效率诉求是**多个功能同时往前推**，不只是「等待时 AI 闲着」。
- 原先「并行要排在可读性之后」的理由（瓶颈在用户注意力）已被 B 的拍板削弱；真正的难点换成了并发冲突（§7）。

### 3.5 工具包反馈回路断了（根子 A 落在工具包上）

- FIELD-LOG 最后一条是 09-28；之后第 4 步的 10 多个 change 零回填，09-27 留的「看免跑一侧会不会漏问题」没人回看。
- change-loop 里两处写着「回报一次后本句由工具包侧删除」的评估位 / 观察位（`skills/change-loop/SKILL.md` 第 57–60 行、第 124–128 行），09-12、09-14、09-22 已回报（09-22 写了「观察位可以关掉」），仍在部署版里——每个 change 都在读过期指令。

### 3.6 回测：外部反方能不能自己发现方向问题

## 6. AI 提议·未定（设计时重新论证，可推翻）

**根子 A（记录回收）**
- 写进热存储前回答三问：谁读、什么时候读、读了做什么；答不出就只写进 commit 或归档。
- 触发交给脚本而不是记忆：观测类 watch 由脚本对照 verify 输出判断；事件类 watch 在路由时由 hook 把绑定该 capability 的条目推到 AI 面前；两种都做不到的不开条目。
- 默认到期：N 周或 M 个 change 未触发 → AI 审 → 移冷存储 → 汇总列出（审与列出已由 §5 第 3 条拍定，N / M 与机制未定）。
- decisions 只留 U 类；AI 的技术决定跟所属 change 归档，判错由真跑暴露（体量约减 2/3）。
- 写新条目前先搜旧条目，防重复和矛盾。
- 清理放进等待期。
- 反方（AI 自己提出的风险）：到期移走可能丢掉几个月后才触发的真问题；但冷存储和 git 里都还在，而现状「全部保留」也没接住它们。

**根子 B（问什么、给什么）**
- 划线标准也许不该是「技术还是非技术」，而是能不能撤回、代价大不大（62 条里只有 6 条难撤回）。
- 生物医学等领域题：先实测已发表综述（项目 09-29 先例），测不出来的攒进给专家的问卷。
- 答案取决于真跑结果的题：真跑前不问，先用默认值跑，跑完再定（对应用户「先选着，真用时再改」）。
- 给 agent 的状态与给人的摘要分开写，给人的不用代号；commit subject 写短。
- 「三行人话」（为什么做 / 做完看到什么不同 / 不做会怎样）可作 AI 自己的刀背检查——写不出人话多半说明不值得做；用户已选「只看里程碑汇总」，所以它是否保留、给谁看未定。

**方向反方的具体形态**
- 人选：至少两个互相独立的外部 agent，最好跨家族（全新 Claude + Codex；跨家族在方向层未测过，依据是项目旧经验）；用最强模型；读原始状态，把约束文档当证据读而不是当指令。
- 机械信号候选（三条在 09-24 前都亮过，前两条 09-19 前就亮了）：同一个证伪实验第 2 次被推迟；判据已达成但工作还在继续；连续几个 change 不碰引擎代码、能力沉在 run 目录。
- 「不是加流程而是换人做」：把 project review 里「停掉的最强理由 / 死胡同 / 贬值」三节交给反方；route check 只保留状态快照。
- 只让多个反方都提到的点进入用户议程（防狼来了）；反方报告不进常驻文档，只有用户定下的方向进 decisions；主会话不转述反方原文（沉没成本会软化）。
- 标定：本次回测可当标定集，换模型或改提示词时在 09-19 / 09-23 快照上重跑；只有一个已知转向，有过拟合风险。

**根子 C（精简）**
- 约束三类：① 产物红线（保留）：不捏造、严格引已入库文献，花钱与不可逆动作要人批准，完成声明附真实输出；② 数据证明有效的机制（保留，精简记录）：fresh-context gate、文件携带跨 session 状态；③ 为防旧失败设的流程（重审）。
- 契约与流程的边界：契约 = 数据格式、CLI 接口、预先登记的测量口径、North Star 红线（必须稳定，换 session 也不能忘）；流程 = 怎么拆 task、写几份文档、每步走什么仪式（交给模型判断）。
- 把 v5 的消融法用到项目层约束：先删、看复发、只加回那一条并注明当时模型；每条约束问「它防哪种失败、近几周在现在的模型上出现过吗」。v5 当年只对工具包提示词用过这个方法。
- spec 分量看风险，只把必须稳定的契约写成 spec；小 change 有 commit 加里程碑汇总就够。主 spec 里冻结能力的部分移冷存储；但约 230 次读取说明 AI 靠主 spec 记住契约，不能一刀切。
- 测试按用户全局规则只覆盖运行时行为；守冻结代码的测试先移出日常 Verify；「承重墙」保留本意（不为变绿弱化失败测试），被测行为删掉时测试可跟着删、commit 写明理由。（按 §5 第 1 条，这些技术细节由 AI 定。）

**根子 D 与工具包回路**
- 主线仍按优先级排但不独占，另设可并行池；等待期 AI 从池里取活（已由 §5 第 7 条拍定只读 / 隔离写的范围）。
- 并行分级：0 级只读并行（反方、探针、测量，无竞争）；1 级写的范围不相交、不碰共享数据的 change 才并行，合入一个一个来；2 级涉及共享数据或热文档的一律串行。——整体属【待琢磨】，见 §7。
- 观察位自带到期日，过期作废，不靠谁记得删。
- 工作流哪里卡或重，在里程碑汇总里留一行，工具包从这里取证；今天这种工作流回顾也放进等待期的池子，不必等用户想起。

**工具包原则候选（来自 §3.7）**
- skill 里不写数据逻辑，数据逻辑放进 CLI 命令。
- 能用真隔离或结构化手段的地方，不用正则审查自由文本。
- 不自定没人要求的契约（与用户全局 CLAUDE.md 一致）。
- 环境知识收拢：项目内的进 CLAUDE.md Stack & Conventions，跨项目的进知识库。

## 7. 待琢磨（不急）

**多 change 并行的设计**。用户原话见 §2。讨论中整理的冲突类型（多线程类比）：

| 共享状态 | 多线程里的对应问题 | 本项目的实例或风险 |
|---|---|---|
| 同一批源文件 | 编译期冲突 | git 合并冲突，看得见，最好处理 |
| 函数的行为或契约 | 数据竞争，不崩溃但结果错 | A 改了 verify 的输出字段，B 还按旧字段读，合并不冲突、跑起来错。串行时已发生过：广度门改成按段计，交付包仍按标注计，被挂进 watchlist |
| 热文档（backlog Now 整段覆盖、主 spec 归档合并） | 非原子「读-改-写」，丢失更新 | 两个 session 各自覆盖 Now；两个 change 改同一条 requirement，后归档的覆盖先归档的 |
| 运行时数据（runs/、ChromaDB、SQLite） | 读到写了一半的状态 | A 真跑时读知识库，B 正在入库或改 schema |
| 测量基准 | 读到中途被改的数据 | A 在冻结产物上标定阈值，B 改了引擎，A 的读数作废 |
| 长时间运行的进程 | 无锁重入 | 单 change 内已出过：判定执行器无锁，中断后重跑新旧两批并发 |
| 「只在绿时提交」 | 互相阻塞 | B 的新测试被 A 改到一半的代码弄红，两边都提交不了 |

对应手段（未定）：隔离（worktree 只隔离代码，数据目录与热文档也要分）、声明读写集合（有交集串行，读写交叉也算）、测量读带哈希的不可变快照、合入设串行点（逐个 rebase + 全量 Verify，抓语义冲突）、热文档每 change 各写各的、里程碑再合。
风险：这套机制本身就是不小的工程，可能变成新的自造复杂度。

**其他**
- 方向反方第一次实战的时机（候选：n=3 开跑前）。用户说「等讨论收尾再定吧」。
- 精简的具体幅度：先量哪些约束近期真防住过什么，再砍。
